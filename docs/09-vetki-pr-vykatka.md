# Ветки, коммиты, PR и выкатка

Принято 23.09.2026, после дня, когда над проектом одновременно работали
несколько сессий. Правила записаны по тем ошибкам, что случились на самом
деле: ветку в общей папке переключили из-под другой сессии, незакоммиченные
правки двух задач смешались в одной рабочей копии, цепочка PR после
squash-вливания пошла в конфликт, на прод ушла сборка, которой не было в
`main`, CI упал на формате, которого не было видно локально.

Главная мысль одна: **у каждой задачи своя папка, своя ветка и свой PR, а
прод — это `main` и ничего больше.**

## 1. Одна задача — своя папка (worktree) и своя ветка

Общая папка `D:\claude\Финашка` (на Маке — своя) — **только для чтения** и
всегда на свежем `main`. В ней не переключают ветки, не делают `stash`, не
оставляют незакоммиченных правок: в этой же папке может работать другая
сессия, и `git switch` у неё под ногами меняет ей все файлы разом.

Работа начинается так:

```bash
git fetch origin
git worktree add ../Финашка-<тема> -b <ветка> origin/main
```

Имя ветки — латиницей по смыслу, как уже принято: `pary-obmen-konspektov`,
`kampus-kak-dannye`. Папку — по той же теме.

Закончили (PR влит) — папку убрать:

```bash
git worktree remove ../Финашка-<тема>
```

Правило «одна сессия — одна папка» важнее удобства. Если сессии нужна чужая
незакоммиченная работа — не брать её из чужой папки, а попросить закоммитить
в свою ветку.

## 2. Коммиты

- **Коммит — сразу, как кусок работает** и тесты зелёные, в своей ветке.
  Незакоммиченная работа — единственное, что можно потерять или смешать с
  чужой.
- Одна задача — одна ветка. Если по ходу понадобилась другая задача —
  новая ветка от `origin/main`, а не «заодно в этой».
- Сообщение — по-русски, объясняет **почему**, а не перечисляет файлы
  (`CLAUDE.md`). Последняя строка — соавтор, если писал ассистент.
- Перед коммитом — **формат по содержимому коммита**, а не по рабочей
  копии. На Windows с `core.autocrlf=true` `gofmt -l` показывает почти все
  файлы из-за CRLF и настоящую ошибку в этом шуме не видно, а CI проверяет
  формат и падает:

  ```bash
  for f in $(git diff --cached --name-only -- '*.go'); do
    git show :"$f" | gofmt -d | head -20
  done
  ```

  Пустой вывод — всё в порядке.
- Shell-скрипты — всегда LF (`.gitattributes`). Новый `.sh` проверить:
  `grep -c $'\r' файл` должен дать 0, иначе серверный bash упадёт на
  `set -o pipefail`.
- Миграция — имя из `date -u +%Y%m%d%H%M%S` в момент создания. Перед PR
  проверить, что в `main` за это время не появилась миграция с тем же или
  более поздним временем; попавшая в `main` миграция неизменяема.

## 3. PR

- **База — `main`.** Один PR — одна тема: так его можно влить, откатить и
  прочитать отдельно.
- Цепочка PR (следующий поверх предыдущего) — только когда без неё никак,
  и это сказано в описании: «стоит поверх #N, потому что …».
- Описание: зачем, что сделано, как проверено; если уже выкачено — так и
  написать.
- **Вливать — squash**, только при зелёном CI. Красный PR не вливается ни
  «на минутку», ни «потом починим».
- CI не запустился (бывает после смены базы PR) — закрыть и открыть PR
  заново (`gh pr close N && gh pr reopen N`), а не пустым коммитом.

### Цепочка после squash

Squash склеивает коммиты базового PR в один новый, и следующий PR цепочки
видит их как чужие — конфликт. Поэтому после вливания базового PR
следующий переносится на новый `main` **только своими коммитами**:

```bash
git fetch origin
git worktree add ../Финашка-rebase -b <ветка>-new origin/main
cd ../Финашка-rebase
git cherry-pick <свои коммиты этого PR>
git diff <ветка>-new <старая голова ветки>      # должно быть пусто
go test ./...
git push --force-with-lease=<ветка>:<старая голова> origin <ветка>-new:<ветка>
gh pr edit <N> --base main
```

`--force-with-lease` с явной ожидаемой головой — чтобы не затереть коммит,
который в эту ветку успела отправить другая сессия. Пустой `git diff` —
доказательство, что перенос ничего не потерял.

## 4. Выкатка

- **Прод = `main`.** Выкатывается только то, что влито в `main`, и только
  из чистой папки на `origin/main` — никогда из рабочей копии с правками.
- Порядок:

  ```bash
  git fetch origin
  git worktree add ../Финашка-deploy origin/main
  cd ../Финашка-deploy
  go vet ./... && go test ./...
  grep -c $'\r' deploy/server/*.sh                 # везде 0
  ssh -i ~/.ssh/schedulefu_deploy root@31.76.6.36 \
    'cd /tmp && sudo -u postgres pg_dump -Fc schedulefu > /root/schedulefu-before-$(date +%F-%H%M).dump'
  bash deploy/server/push.sh
  cd .. && git worktree remove Финашка-deploy
  ```

- После выкатки — проверить, а не поверить: `health`, новые экраны отвечают
  200, в журнале службы нет ошибок
  (`journalctl -u schedulefu --since "-5 min" | grep -iE "error|panic"`),
  новая функция открыта на боевых данных. В PR — комментарий «выкачено
  ДД.ММ, что проверено».
- Срочно нужно выкатить невлитое — значит, сначала влить. Если совсем
  никак: сборочная ветка из закоммиченных веток, и **в тот же день** PR по
  каждой, чтобы `main` догнал прод. Незакоммиченное на прод не уходит
  никогда.
- Резервная копия перед выкаткой обязательна, даже если миграция «только
  добавляет колонку».

## 5. Чей это репозиторий

Репозиторий принадлежит другу автора, автор — соавтор с правом записи.
Поэтому отправка в GitHub, открытие и вливание PR, выкатка на прод — **только
по явной просьбе автора в этой сессии**. Разрешение на одну выкатку не
распространяется на следующую.
