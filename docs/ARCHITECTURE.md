# Архитектура ScheduleFU

Канон устройства системы. Принят 21.09.2026 после недели работы первой
версии и сверки с соглашениями Akeda ERP. Новый код обязан ему следовать;
существующий приводится к нему по плану в § 10, не переписыванием.

Документ отвечает на три вопроса: из чего система состоит, кому что
разрешено знать, и куда она растёт, не ломая себя.

## 0. Что это и чем не является

ScheduleFU — **зеркало** расписания Финансового университета с человеческим
интерфейсом и функциями, которых у источника нет: свободные аудитории,
уведомления об изменениях, календарная подписка, «где преподаватель».

Источник истины — `ruz.fa.ru`. Мы его читаем, сравниваем со вчерашним и
показываем. Мы его **не ведём**. Из этого следует всё остальное:

- нет конструктора расписания, версий, валидации конфликтов, заявок
  преподавателей, ролей учебной части — этого не будет и через три года,
  потому что писать в источник нам некуда;
- нет аккаунтов с паролями — закрепление живёт на устройстве, подписка
  привязана к устройству;
- «изменение» существует только относительно того, что мы уже знали;
- сколько бы данных мы ни собрали, архивом вузовской базы они не становятся
  ([03-legal-risks.md](03-legal-risks.md)): храним текущее окно и журнал
  на месяц.

Это отличает нас от Planovo KEMS, где учебная часть сама составляет
расписание. Общие у двух систем — решения, не код.

## 1. Почему Go и что значит «совместимость с Akeda»

Язык — Go, потому что на нём написана Akeda ERP, крупнейший проект автора,
и продукты должны уметь стыковаться. Важно точно понимать, **на каком
уровне** стыковка нужна, иначе мы притащим в маленький сервис чужие
зависимости ради совместимости, которой никто не пользуется.

| Уровень | Нужна ли совместимость | Что делаем |
|---|---|---|
| Язык и тулчейн | да | Go, тот же тулчейн, `go.work`-совместимый layout |
| Соглашения о модулях | да | тот же канон: `domain/ · interfaces.go · service.go · infrastructure/postgres/`, порты, один писатель у таблицы, миграции таймстемпами |
| Данные на границе | да | ICS, JSON `/api/v1`, стадии операций `internal / preview / public` |
| Библиотеки домена | по факту | `webpush-go` уже совпадает; `ical` при появлении третьего продукта уезжает в общий модуль |
| HTTP-фреймворк, DI, логгер | **нет** | см. § 4 — это единственное сознательное расхождение |

Стыковка — это возможность Akeda прочитать наш календарь, вызвать наш API и
однажды показать расписание у себя в кабинете. Ни один из этих сценариев не
требует, чтобы оба сервера были на Fiber.

## 2. Форма: модульный монолит, один бинарник

Одно приложение, один `go.mod`, один исполняемый файл `schedulefu` с
подкомандами:

```
schedulefu serve       HTTP: страницы, /api/v1, отправка уведомлений
schedulefu collect     обход источника, слепок, изменения, очередь уведомлений
schedulefu static      сборка версии для GitHub Pages
schedulefu vapid       ключи уведомлений
schedulefu migrate     миграции без запуска сервера
```

Почему один бинарник, а не два, как сейчас: деплой — это один файл и один
`systemd`-юнит на роль; версия у всех ролей одна и та же по построению;
composition root один, и он единственный, кто знает все модули поимённо.

Почему монолит, а не сервисы: 5 800 строк кода, 2 ядра, 300 запросов в
секунду с запасом. Сервисы решают проблемы, которых у нас нет, и создают
те, которых нет тоже. Akeda пришла к тому же на 300 000 строк.

Модули **не** получают свои `go.mod`, пока проект не пересечёт порог, на
котором это сделала Akeda (модуль обходится контрактами и его собирает
отдельная команда). До тех пор границу держит тест графа зависимостей
(§ 6), а не компилятор — этого достаточно.

## 3. Слои и модули

```
cmd/schedulefu/                    composition root: знает все модули поимённо
internal/presentation/             транспорт — зависит от модулей ↓
    web/        HTML-страницы (html/template, без JS кроме подписки)
    api/        JSON /api/v1
    static/     сборка для Pages
internal/modules/                  домен — модули зависят друг от друга только через порты
    source/     адаптеры источников расписания (ruz)
    schedule/   ядро: слепки, пары, аудитории, площадки, изменения, сетка пар
    notify/     подписки и доставка уведомлений
    export/     календарь ICS
    feedback/   «на самом деле занято» (план, § 9)
internal/platform/                 слой-нейтральное — доступно всем
    config/     YAML + env
    db/         пул, миграции
    httpx/      заголовки безопасности, сжатие, ограничение частоты
    clock/      часовой пояс вуза, русские даты
```

Направление зависимостей одно: `presentation → modules → platform`.
Модуль не импортирует `presentation` никогда. `platform` не импортирует
никого.

### 3.1 `source` — адаптеры источников

Порт, который зовёт `schedule`:

```go
type Source interface {
    Search(ctx, kind SearchKind, term string) ([]SearchResult, error)
    Schedule(ctx, kind Kind, id int64, from, to time.Time) ([]Lesson, error)
    ParseAuditorium(name, building string) Auditorium
}
```

Реализация `source/ruz` — текущий `internal/ruz` целиком: клиент, ловушка
с GUID преподавателя (`SearchPerson` намеренно не объявлен), разбор имён
аудиторий, площадки, отсев мусора. Всё знание о странностях источника
живёт здесь и не просачивается выше: `schedule` получает уже чистые
структуры.

**Заложенный рост.** `ruz.fa.ru` — тиражная платформа: тот же API стоит в
ВШЭ, СПбПУ, САФУ, ГУЗ. `Source` с параметром `BaseURL` и своей таблицей
правил разбора этажей — это один код на несколько вузов. Второй вуз
добавляется конфигом и таблицей площадок, не форком. Это единственное
место, где мы закладываем рост заранее: он бесплатный.

### 3.2 `schedule` — ядро

Владеет таблицами `lessons`, `lesson_changes`, `auditoriums`, `groups`,
`lecturers`, `collector_runs`. Только этот модуль в них пишет.

Домен (`schedule/domain`): `Lesson`, `Auditorium`, `Site`, `Group`,
`Lecturer`, `Change`, `Subject` (группа или преподаватель — то, чьё
расписание закрепляют), `Slot` и сетка пар, `RoomView` (полоса занятости).

Сервисы: сбор слепка и его применение с поиском изменений (сегодняшние
`collector` + `store.ApplySnapshot`); запросы — свободные аудитории,
расписание владельца, «где преподаватель», занятость аудитории.

Что `schedule` отдаёт другим модулям портами (объявляет вызывающий,
реализует `schedule`):

```go
// notify зовёт:
type ChangeReader interface {
    ChangesSince(ctx, since time.Time, limit int) ([]Change, error)
}
// export зовёт:
type ScheduleReader interface {
    ScheduleFor(ctx, subject Subject, from, to time.Time) ([]Lesson, error)
    LecturerName(ctx, oid int64) (string, error)
}
```

`Subject` живёт здесь, а не в транспорте: это язык домена («чьё
расписание»), им говорят и подписки, и календарь, и cookie. Сейчас он в
`web`, и из-за этого `api` импортирует `web` — транспорт зависит от
транспорта. Переезд `Subject` в `schedule/domain` эту петлю снимает.

### 3.3 `notify` — подписки и доставка

Владеет `push_subscriptions`, `push_outbox`. Три части: планировщик
(изменения → одно письмо на адресата), очередь с блокировкой строк,
отправщик. Ключ адресата — `Subject.Key()`.

Транспорт — порт:

```go
type Transport interface {
    Send(ctx, target Target, n Notification) (Outcome, error)
}
```

Сейчас одна реализация — Web Push. Telegram и почта добавляются как
реализации того же порта, без изменений в планировщике и очереди.
Очередь хранит `transport` и `target` в строке письма, а не только
push-endpoint — это единственная правка схемы под будущий рост, и она
дешёвая, поэтому делается при переезде.

### 3.4 `export` — календарь

`ical` без изменений плюс сервис, собирающий календарь владельца через
`ScheduleReader`. Знает только `schedule/domain`.

### 3.5 `presentation`

`web` — HTML, серверный рендеринг, работает без JavaScript; JS есть ровно
один — подписка на уведомления. `api` — JSON `/api/v1` по правилам § 7.
`static` — то же, что `api` и `web` знают о данных, но упакованное в файлы
для Pages; клиентский `app.js` повторяет логику сетки пар осознанно —
на Pages запустить Go нечем.

Транспорт не содержит доменных правил. Если в обработчике появляется
`if` про расписание — он переезжает в модуль.

## 4. Стек

| | Выбор | Почему |
|---|---|---|
| HTTP | `net/http`, роутер стандартной библиотеки (Go ≥ 1.22) | Fiber в Akeda стоит на fasthttp и несовместим с `net/http`-экосистемой: `httptest`, middleware, `http.Handler`. Нам он не даёт ничего — 313 запросов в секунду на двух ядрах со стандартной библиотекой — а стыковка с Akeda идёт через API, не через фреймворк. Это **единственное сознательное расхождение** с Akeda, и оно записано здесь, чтобы не обсуждать его заново |
| Композиция | явная, в `cmd/schedulefu` руками | fx оправдан на семнадцати модулях; на пяти он прячет порядок инициализации, который лучше видеть |
| Конфиг | YAML + переменные окружения с префиксом `SCHEDULEFU_` | тот же приём, что `AKEDA_GO_*`: файл для стенда, env для секретов и переопределений. `gopkg.in/yaml.v3` и сорок строк накладки; viper тянет пять зависимостей ради того же |
| Логи | `log/slog` | стандарт с Go 1.21, структурированный, без зависимостей. Akeda на zap; логи двух продуктов никто не склеивает |
| База | PostgreSQL 16+, `pgx/v5` | как Akeda; `pgkit` оттуда переиспользуем при появлении общего модуля, пока — свои сорок строк |
| Миграции | SQL в `go:embed`, имя **`YYYYMMDDHHMMSS_описание.sql`** из `date -u`, применяются при старте и командой `migrate` | как Akeda, и по той же причине: сквозной номер `0004_` две параллельные ветки выберут одинаково и уронят мигратор. Попавшая в `main` миграция неизменяема — исправление только новой |
| Тесты | `testing` стандартной библиотеки, интеграционные — на настоящем PostgreSQL, своя база на пакет | testify ничего не добавляет к `t.Fatalf`; своя база на пакет — потому что `go test` гоняет пакеты параллельно, и на общей базе тесты роняли друг друга |
| Уведомления | `webpush-go` | совпадает с Akeda — калькой |
| Обратный прокси | Caddy | автоматический сертификат; без HTTPS не работают ни push, ни установка на телефон |

Зависимостей вне стандартной библиотеки — три: `pgx`, `webpush-go`,
`yaml.v3`. Каждая новая объясняет в PR, что она делает такого, чего
стандартная библиотека не может.

## 5. Данные

**Один писатель у таблицы** — модуль-владелец. Чужой модуль читает через
порт владельца или, для отчётных запросов, напрямую по договорённости,
записанной в `interfaces.go` читающего.

| Таблица | Владелец | Срок жизни строк |
|---|---|---|
| `lessons` | schedule | текущее окно сбора (неделя вперёд); ушедшее из окна удаляется при следующем проходе |
| `lesson_changes` | schedule | 30 дней |
| `auditoriums`, `groups`, `lecturers` | schedule | справочники, живут; `last_seen_at` для чистки исчезнувших |
| `collector_runs` | schedule | 90 дней |
| `push_subscriptions` | notify | пока живо устройство; мёртвые (404/410) удаляются немедленно |
| `push_outbox` | notify | 7 дней после доставки или отказа |
| `room_reports` (план) | feedback | до конца дня, о котором сообщение |

Правила, продиктованные тем, что данные чужие:

- **не архивируем**: окно сбора — неделя, журнал — месяц, старое удаляется,
  а не переносится в «холодное хранилище»;
- **первое наполнение не журналируется** и не порождает уведомлений:
  появление данных у нас — не правка вуза; то же для дня, впервые
  вошедшего в окно;
- **сравнение слепков по отпечатку значимых полей**, служебные поля
  источника (`author`, `createddate`) в отпечаток не входят;
- **никаких досье**: у подписки только адрес доставки и ключи шифрования,
  ни IP, ни браузера, ни истории просмотров.

Резервные копии — `pg_dump` раз в сутки, хранить 14 дней. Терять нечего,
кроме подписок: расписание пересобирается за две минуты.

## 6. Правила зависимостей и как они держатся

1. `presentation → modules → platform`; обратных рёбер нет.
2. Модуль → модуль только через порт: интерфейс объявлен в `interfaces.go`
   **вызывающего**, реализация — у владельца, связывание — в
   `cmd/schedulefu`. Модуль не импортирует пакет другого модуля.
3. `source` не знает о `schedule`. `schedule` зовёт `Source`.
4. `platform` не импортирует `internal/modules` и `internal/presentation`.
5. Никакой пакет не импортирует `cmd`.

Держит это **тест графа** в `internal/archtest`: `go list -deps` по всем
пакетам, проверка пяти правил, падение сборки при нарушении. Это дешёвый
аналог depguard в Akeda; когда модули получат свои `go.mod`, тест станет
лишним — граница перейдёт к компилятору.

## 7. API и стадии

`/api/v1/*`, JSON, без авторизации на чтение (данные публичные), запись —
только подписки, с проверкой адреса доставки.

Каждая операция имеет стадию, как в Akeda:

- **internal** — не описана, обещаний нет, меняется свободно; всё
  неописанное — internal по умолчанию;
- **preview** — описана в `docs/api/openapi.yaml`, работает, форма может
  измениться;
- **public** — форма зафиксирована; удаление поля, смена типа, новое
  обязательное поле — ломающие изменения; снятие только через пометку
  устаревшей и шесть месяцев жизни.

Сейчас всё internal. Первым в `preview` уходит то, что нужно Akeda для
стыковки: расписание владельца и календарь. Листание — только `limit` с
объявленным потолком; без потолка внешний код вправе попросить миллион
строк.

Правило одно на оба продукта, чтобы разработчик Akeda-приложения, читающий
наш API, не учил второй набор обещаний.

## 8. Стыковка с Akeda: три горизонта

**Сейчас, без единой строки кода.** Модуль `calendar` в Akeda разбирает ICS
и подключает внешние календари. Наша ссылка `/calendar.ics?group=…` —
готовый источник для него: расписание группы или преподавателя появляется в
календаре кабинета как подписка и обновляется раз в час.

**Средний горизонт.** Akeda-приложение (Extension SDK) показывает
расписание преподавателя в его кабинете, читая наш `/api/v1` по API-ключу.
Для этого нужны: операции стадии `preview`, ключ доступа с ограничением
частоты, OpenAPI-описание. Наши события (изменение расписания) идут в Akeda
через наш `notify` с транспортом «webhook с подписью» — по контракту
`outbox` Akeda, а не своим форматом.

**Дальний горизонт.** Если появляется третий продукт на Go, общие вещи —
`ical`, обвязка `webpush`, `httpx` — уезжают в отдельный Go-модуль по
образцу `backend/contracts` Akeda. **Не раньше**: общий модуль на два
продукта — это две команды, договаривающиеся о каждой правке, ради экономии
трёхсот строк.

Чего мы не делаем: не встраиваем ScheduleFU в монорепозиторий Akeda, не
делаем его модулем ERP. У них разные владельцы данных, разный ритм и разная
юридическая природа; сшивать их в один процесс — значит нести риски одного
в другой.

## 9. Куда растёт система

Заложено сейчас, стоит дёшево или бесплатно:

| Рост | Что уже есть под него | Что добавить |
|---|---|---|
| Второй вуз на платформе РУЗ | порт `Source`, `BaseURL` в клиенте | таблица площадок и правил этажей второго вуза; `university` в конфиге и в ключах подписок |
| Telegram-бот | `presentation` как слой; `Transport` в `notify` | `presentation/telegram` и `notify/telegram` — два адаптера, ни одной правки в домене |
| Почта как транспорт уведомлений | порт `Transport` | одна реализация |
| «На самом деле занято» | предупреждение уже на экране | модуль `feedback`: `room_reports`, порт `RoomOverride`, который `schedule` учитывает в выдаче свободных; строка живёт до конца дня |
| Синхронизация закреплений между устройствами | `Subject.Key()` как единый ключ | опциональный аккаунт **без пароля** — ссылка на почту или код; закрепления и подписки переезжают с устройства на человека. Делается только если попросят: сейчас это решение стоит дороже проблемы |
| Аналитика занятости («в какое время 3 этаж обычно свободен») | слепки | агрегаты по слотам, без хранения сырых пар за прошлое — иначе это архив, § 5 |

Не заложено намеренно, и заложить — ошибка: конструктор, аккаунты с
паролями, мультитенантность в одной базе, i18n, мобильные нативные
приложения (PWA закрывает это).

## 10. План перехода от текущего кода

Каждый шаг оставляет систему рабочей и заканчивается зелёными тестами и
выкладкой. Это переезд, не переписывание: доменная логика (`ApplySnapshot`,
сетка пар, разбор аудиторий, планировщик уведомлений, ICS) переезжает
файлами.

1. **Один бинарник.** `cmd/schedulefu` с подкомандами, четыре старых `cmd/*`
   становятся его функциями. Внутри ничего не меняется. Обновляются
   `deploy/local` и скрипт Pages.
2. **`platform`.** `httpx` переезжает как есть; появляется `config`
   (YAML + `SCHEDULEFU_*`), `db` (открытие, миграции по таймстемпам —
   существующие три миграции переименовываются по датам их коммитов),
   `clock` (часовой пояс, русские даты из `web/dates.go`).
3. **`source/ruz`.** Переезд `internal/ruz` плюс порт `Source`.
   `store` перестаёт импортировать `ruz`: разбор аудиторий делает
   `schedule` через порт.
4. **`schedule`.** Слияние `store` (кроме подписок), `collector`,
   `web/slots.go`, `web/subject.go` в модуль по канону. Это самый большой
   шаг и единственный, где меняется структура кода, а не только пути.
5. **`notify`, `export`.** Отделение от `store` через порты `ChangeReader`
   и `ScheduleReader`; в очередь добавляются `transport`/`target`.
6. **`presentation`.** `web`, `httpapi → api`, `staticgen → static`;
   `api` перестаёт импортировать `web`; тест графа зависимостей включается
   и с этого момента держит границы.

После шестого шага структура совпадает с § 3, и дальше правило простое:
новая функция — либо новый модуль, либо новый порт у существующего.

## 11. Как мы работаем

Короткая версия правил; полная — в `CLAUDE.md`.

- Замер до оптимизации. Каждое «стало быстрее» — с цифрами до и после.
- Тест на найденный баг пишется до исправления и называется по-русски тем,
  что он закрепляет.
- Комментарий объясняет **почему**, особенно там, где решение продиктовано
  странностью источника.
- Коммит объясняет причину изменения, а не перечисляет файлы.
- Когда ошибся в выводе — сказать прямо и в том же сообщении.
- Данные из источника — чужие и недоверенные: экранируются везде, где
  попадают в разметку; политика безопасности запрещает инлайновые стили
  и скрипты и не ослабляется ради удобства.
