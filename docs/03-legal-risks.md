# Юридические риски и как их снижать

Ниже — не юридическая консультация, а рабочая карта рисков по итогам
ресёрча, чтобы принимать решения по архитектуре и охвату проекта осознанно.
Для реальных юридических гарантий стоит консультироваться с юристом,
особенно перед публичным запуском.

## 1. Ст. 272 УК РФ («неправомерный доступ к компьютерной информации»)

- Состав требует преодоления защиты (пароль, обход технических средств
  защиты).
- Раз `ruz.fa.ru` открыт для просмотра без обязательной авторизации,
  простое обращение к нему (даже автоматизированное) этот состав не
  образует.
- Риск появляется, если вместо этого использовать личный кабинет
  `org.fa.ru` с логином/паролем студента для автоматизированного сбора —
  это уже другая история (доступ по чужим/личным учётным данным массово,
  для целей, не предусмотренных пользовательским соглашением). Вывод:
  не использовать `org.fa.ru` как источник, раз есть открытая
  альтернатива.

## 2. Ст. 1334 ГК РФ — исключительное право изготовителя базы данных

- Это главный реальный риск проекта.
- Даже если каждая отдельная запись расписания общедоступна,
  систематическое извлечение существенной части базы данных вуза
  (расписание всех групп на весь семестр) и republication в виде
  отдельного продукта может быть расценено как нарушение права
  изготовителя базы данных.
- Ориентир из практики: дело «ВКонтакте против Дабл» — суд признал
  незаконным систематический парсинг с извлечением существенной части
  базы данных (фактура другая — там были и персональные данные, — но
  логика судов по поводу «существенной части базы» релевантна).
- **Как снижать риск:**
  - Забирать данные на актуальный день/ближайшую неделю, а не архивировать
    расписание целиком на длительный период.
  - Ограничивать охват одним корпусом на MVP-этапе, а не всем вузом сразу.
  - Не публиковать сырое расписание как есть (это была бы прямая
    republication базы) — публиковать производный, переработанный
    результат («свободно / занято» по аудиториям), а не таблицы пар.
  - Как только появится рабочий прототип — выходить на диалог с вузом
    вместо того, чтобы масштабировать проект втихую. Партнёрство/
    согласие снимает этот риск полностью.

## 3. robots.txt

- Автоматическое обращение к `ruz.fa.ru` инструментами веб-доступа
  заблокировано его правилами robots.txt.
- Юридической силы закона это не имеет, но это явный сигнал позиции вуза
  по поводу автоматического сканирования — сервис, который его игнорирует,
  выглядит менее добросовестно в глазах вуза при возможном конфликте.
  Дополнительный аргумент в пользу открытого диалога, а не тихой работы.

## 4. Персональные данные (ФИО преподавателей)

- Расписание содержит ФИО преподавателей — формально персональные данные.
- Риск низкий, поскольку вуз сам публикует эти данные в тех же целях (кто
  где ведёт занятия), и republication той же информации в том же
  контексте (расписание) обычно не требует отдельного основания.
- Не стоит расширять это дальше — не собирать и не публиковать что-либо
  сверх того, что уже есть в расписании (например, не строить «профиль
  преподавателя» на основе агрегированных данных).

## 5. Товарный знак / фирменное наименование

- Использование названия «Финансовый университет», его логотипа или
  визуального стиля в оформлении сервиса без согласования — риск, если
  сервис выглядит как официальный продукт вуза.
- **Рекомендация:** на этапе, пока нет партнёрства с вузом, использовать
  нейтральное название и оформление, явно указывать неофициальный статус
  проекта.

## 6. Общая стратегия снижения риска

1. Узкий MVP без публичного анонса — тестирование гипотезы на своих же
   одногруппниках, без огласки.
2. Минимально необходимый объём данных (день/неделя, один корпус), не
   полная копия базы вуза.
3. Публикация производного результата, а не сырых данных расписания.
4. Как только продукт работает — переход к открытому диалогу с деканатом/
   ИТ-отделом/студсоветом, а не к тихому масштабированию. Это тот же путь,
   которым, судя по всему, шло приложение «Кампус» (через программу
   поддержки студенческих стартапов) — см. `05-roadmap.md`.
