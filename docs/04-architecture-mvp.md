# Механика и план MVP

> **Устарело частично (12.09.2026).** Обратный индекс (п. 3) и ручной обход
> здания (п. 1) не нужны — см. `06-api-findings.md`. Скоуп также расширен:
> проект делается как полноценная замена ruz.fa.ru, а не только «свободные
> аудитории».

## Задача

Для заданной аудитории и момента времени ответить: свободна она сейчас
или нет, и если занята — до какого времени.

## Компоненты

### 1. Справочник аудиторий (статичные данные)

Таблица: `корпус | этаж | номер кабинета | вместимость | тип (лекционная /
компьютерный класс / прочее)`.

Готового открытого источника нет. Два способа наполнения, не
взаимоисключающих:

- **Ручной обход здания** на Ленинградском, 49 — самый надёжный способ,
  даёт полный список даже тех кабинетов, где почти не бывает пар.
- **Автоматическая агрегация** уникальных значений поля «аудитория» из
  выгрузок расписания — быстрее, но неполно (кабинет без пар не попадёт
  в список) и может содержать «мусорные» значения (онлайн-формат,
  опечатки деканата и т. п., которые надо будет чистить).

Для MVP можно начать со второго способа и дополнять первым по мере
надобности.

### 2. Сбор расписания (регулярный процесс)

- Источник: `ruz.fa.ru`, через готовую библиотеку `fa_api` (или
  собственный клиент по её образцу, если структура ответа не подходит).
- Проходим по всем группам (и, возможно, отдельно по преподавателям —
  для перекрёстной проверки) главного корпуса, тянем расписание на
  актуальный период (день/ближайшая неделя — см. `03-legal-risks.md`,
  почему не весь семестр).
- Складываем в свою базу: `(аудитория, корпус, дата, время начала, время
  конца, группа/предмет)`.
- Периодичность обновления: не реже раза в 15–60 минут — расписание
  меняется задним числом (замены, переносы), это нормальная практика
  деканатов.

### 3. Построение обратного индекса

Группировка собранных записей по аудитории → отсортированный список
занятых интервалов на дату. «Свободна сейчас» = для текущего момента
времени нет пересекающегося интервала. Так как пары идут фиксированными
слотами, это простая арифметика по времени, без сложной логики.

### 4. Слой неопределённости (важно не пропустить)

Отдельно фиксируем, что у сервиса есть известный предел точности:
внерасписные бронирования (мероприятия, экзамены, ремонт) не отражены в
`ruz.fa.ru` и, соответственно, в индексе. Варианты компенсации:

- explicit-дисклеймер в интерфейсе («данные ориентировочные, свежесть —
  N минут назад»);
- пользовательская обратная связь — кнопка «на самом деле занято»,
  которая временно помечает аудиторию как занятую до проверки;
- в перспективе — договорённость с вузом о доступе к системе
  бронирования (см. `05-roadmap.md`).

### 5. Выдача результата

Форма подачи (сайт, Telegram-бот, что-то ещё) — по словам пользователя,
вопрос вторичный и решается отдельно, когда механика уже работает.
Разумный минимум для MVP: простая страница/таблица «кто свободен сейчас»
на выбранный корпус, без необходимости сложного UI на старте.

## Этапы (укрупнённо)

1. **Технический пилот** (несколько дней): установить `fa_api`, вытащить
   расписание 10–20 групп главного корпуса, посмотреть реальную
   структуру ответа — есть ли поле аудитории/корпуса и в каком виде.
   Это снимает последний открытый технический вопрос.
2. **Справочник аудиторий** для одного корпуса — вручную или через
   агрегацию (см. выше).
3. **Сборщик расписания** + обратный индекс + простая выдача на один
   день, без автообновления — первая рабочая версия для проверки логики
   на реальных данных.
4. **Автоматизация обновления** + расширение на весь корпус.
5. **UI/бот** — на усмотрение, когда логика уже надёжна.
6. **Проверка спроса** на узком кругу (свои же группы/факультет), без
   публичного анонса.
7. **Диалог с вузом** с готовым прототипом (см. `05-roadmap.md`).
